# HTTP caching

Updated: 5 November 2026. This applies to the independent Flashloop runtime in `apps/flashloop`. The published GitHub Pages frontend and newer deployment checkout were not changed.

## Policy

`src/lib/http/cache-policy.ts` defines the private response policy. Browser `Cache-Control` is `private, no-store`; `CDN-Cache-Control` and `Vercel-CDN-Cache-Control` are both `no-store`. `Pragma: no-cache` and `Expires: 0` support older intermediaries. The response helper preserves existing RSC `Vary` values and adds `Cookie` and `Authorization` defensively. Variation is not authorization: every protected request still validates the current session and ownership through the existing store and RLS.

All `/api`, `/auth`, and `/account` paths, including nested and future routes, receive this policy from the runtime Proxy and Next.js header configuration. This covers account balances, project/job metadata, upload and signed-download responses, callbacks, webhooks, Inngest, quota denials, redirects, configuration failures, and framework-generated 404/405 responses. Refreshed authentication cookies survive the Proxy response replacement without dropping the private policy. Origin-proof denials are private even when the requested path was public.

The shared `boundedProviderFetch` now forces `cache: "no-store"` and removes Next.js `next` caching options, even when a caller supplies `force-cache`, tags, or revalidation. Its existing deadlines and cancellation behavior remain active. No authentication decision or user data response is stored in a Next Data Cache, React cache helper, or application HTTP cache.

The public `/` and `/blue` marketing pages contain no server-side account state and retain Next.js static-page caching. Their content changes with a new deployment. Next.js-generated `/_next/static/` JavaScript, CSS and font assets contain build/content versions and retain Next.js's `public, max-age=31536000, immutable` policy. Source assets under `/sites/` use `public, max-age=0, must-revalidate`, with ETags supplied by the server. Existing filenames such as short hash prefixes are source identifiers, not verified content hashes; they do not receive immutable caching. A future public content API must receive an explicit public allowlist and bounded TTL rather than weakening the default private `/api` policy.

R2 storage already writes private/no-store object metadata and signs downloads with `ResponseCacheControl: "private, no-store"`; this task did not enable or exercise R2. See [STORAGE.md](STORAGE.md). Signed links are bearer capabilities until expiry; an uncached signing response does not make a copied live URL account-bound.

## Deployment rules

The runtime policy requires a Next.js deployment. `STATIC_EXPORT=true` excludes runtime headers and routes; GitHub Pages controls its own public static response headers and cannot host the private API. No Pages security claim follows from these tests.

Follow [CLOUDFLARE_SETUP.md](CLOUDFLARE_SETUP.md#http-caching): bypass caching for `/api`, `/auth`, `/account` and all descendants; preserve origin no-store on errors and redirects; do not deploy Cache Everything or Worker rules that override it. Do not put account/session values or origin secrets into cache keys. Inspect both Cloudflare and Vercel after deployment. Preserve Next.js RSC headers, `Vary`, and the `_rsc` query discriminator; never merge HTML and RSC cache variants. A protected response must reach authorization on every request rather than be served before the origin check.

The auth UI currently performs full-document navigation after successful signin/signout rather than retaining a previous account's client Router Cache. No service worker is registered by this source. HTTP no-store does not prevent a future service worker from explicitly writing data to Cache Storage, and modern browsers can have separate back/forward page restoration policies. Do not add offline storage of authenticated pages, account API responses, or signed links. Browser history and back/forward restoration still require a real staging browser test; no-store headers alone are not evidence that every browser history implementation was exercised. Test pre-existing service workers at the deployed origin as well as a clean profile.

## Verification record

Read the installed Next.js **16.4.5** documentation before editing: Route Handlers, CDN caching, caching without Cache Components, the `headers` configuration, and the `proxy` file convention. In particular, the docs distinguish hashed immutable framework assets from mutable public files and require private routes behind an upstream CDN to bypass caching.

- `node --test tests/http-caching.test.cjs`: **5 tests passed**. These exercise private headers across successful/error/redirect statuses, preserved RSC variation and cookies, private path/base-path classification, account-cookie refresh/redirect/configuration failure, and sequential two-principal requests through the actual ownership handler/store with controlled browser/CDN cache models. A positive control demonstrates that the modeled cache retains an unprotected success across accounts, including heuristic caching without max-age. With the actual policy, account A warms a URL; B gets 404, anonymous gets 401, and revoked A gets 401. Each call revalidates the session and neither modeled cache stores a response. These controlled models do not establish real browser, CDN, hosted Auth, or RLS behavior.
- `node --test tests/provider-fetch.test.cjs tests/edge-origin.test.cjs`: **29 tests passed**. These include forced no-store despite caller caching options, mandatory deadlines/cancellation, and private origin-proof denials.
- `npx tsc --noEmit` and focused ESLint on the cache helper, Proxy, and provider-fetch files passed.
- After the fresh normal production build, `node scripts/verify-http-caching.mjs` passed **28 real local HTTP checks** under **Node.js 24.22.2**. These cover statically built auth pages, account pages, APIs including analytics, framework 404/405/OPTIONS, disabled signed-download/generation/webhook routes, synthetic cookie jars against disabled accounts, public marketing HTML, versioned Next.js assets and mutable-asset ETag 304 revalidation. Wrapped APIs issued distinct UUID request IDs and replaced the untrusted incoming fixture ID. No hosted credentials were supplied to this runner.
- `SUPABASE_CLI_BIN=<trusted CLI path> OWNERSHIP_TEST_ROUTES=true node scripts/verify-ownership-provider.mjs` passed **69 real staging assertion groups**, including **23 local production Next.js Route Handler groups**, under **Node.js 24.22.2** and Supabase CLI **3.0.0**. The existing Kumi staging schema supported the ownership test. Two disposable Auth identities obtained real signed sessions and completed trusted fixture verification. Both directions warmed the same project/job/upload/output URL as its owner, then sent the foreign account and anonymous caller to that identical URL, including conditional validators; foreign calls returned 404, anonymous calls 401, and no private record was returned. Account/profile URLs alternated identities and returned the corresponding account. Existing signed cookies were denied immediately after revocation. Every tested private response carried browser/CDN no-store; no positive Age or cache HIT/STALE was observed. Disposable sessions, identities and dependent rows were removed successfully.
- The real-session cache group deliberately avoided request-side cache bypass. A separate loopback Node.js 24 HTTP probe confirmed that its manual conditional requests sent neither request `Cache-Control` nor `Pragma`. The first runtime-runner attempt received 200 for public conditional revalidation because Fetch automatically added request no-cache to a manually conditional request; the runner's explicit mode was corrected and the public asset returned 304. The server policy did not change for that correction. The hosted runner was rerun after the same request-mode correction and all 69 groups passed again with cleanup.

## Remaining acceptance gates

1. Deploy the reviewed runtime to the isolated staging origin without changing the existing Pages release or production alias. Verify no intermediary overrides the private policy, including origin-denial/error/redirect paths.
2. Use two disposable, genuinely verified staging accounts with distinct projects and balances. Warm A's exact account/project/job/upload/output/signed-link URLs without request-side `Cache-Control: no-cache` or disabled browser caching. Alternate B and anonymous calls at the identical URL; require denied foreign access and no A values. Repeat in reverse, after logout/revocation, in separate browser profiles and after switching accounts in one profile, including back/forward restoration. Capture only safe status/header/assertion summaries.
3. Repeat through the actual Cloudflare and Vercel chain. Private responses must have no positive `Age` and no `HIT`/`STALE` cache result, and must never return 304 based on another account's private representation. Public marketing pages/assets should retain intended caching. Test both HTML and RSC navigation/prefetch variants.
4. Once R2 is enabled, test actual signed-download expiry and response headers in the browser, without logging or storing the URL. Do not infer private media protection from the disabled storage route.

The staging-backed HTTP checks establish current local Route Handler behavior with real sessions and hosted RLS. They do not establish deployed browser or CDN cache behavior. No runtime deployment, real browser cache, deployed CDN cache, signed R2 response, or production security acceptance was verified. Missing runtime/edge/storage setup remains a release gate.
